# ADR-0006: One `weather_readings` table with a natural key and idempotent upserts

- **Status:** Accepted
- **Date:** 2026-11-22

## Context

The assessment says one table is enough. The table must still be well structured: correct types, constraints, sensible indexes for the queries the REST API will run, and no duplicates when the same city is fetched several times.

OpenWeather refreshes a city's observation only every few minutes, so two calls close together return the **same** observation (same `dt`). The same observation can also be requested in different unit systems.

## Decision

A single table, `weather_readings`, one row per *observation in a unit system*:

| Group | Columns | Notes |
|---|---|---|
| Identity | `id BIGINT GENERATED BY DEFAULT AS IDENTITY` | Surrogate primary key, used by `GET /weather/{id}` |
| Location | `city_id`, `city_name`, `city_search_name`, `country_code`, `latitude`, `longitude` | `city_search_name` is the lower-cased, accent-free name |
| Time | `observed_at TIMESTAMPTZ`, `fetched_at TIMESTAMPTZ DEFAULT now()` | When OpenWeather measured vs. when we collected |
| Context | `units`, `lang` | Needed to interpret the values and the description |
| Measurements | `temperature`, `feels_like`, `temp_min`, `temp_max`, `wind_speed` (`NUMERIC(6,2)`); `humidity`, `pressure`, `wind_deg`, `cloudiness` (`SMALLINT`) | Exact decimals, no float rounding surprises |
| Condition | `weather_main`, `weather_description` | Primary condition only |
| Audit | `raw_payload JSONB` | The full original response |

**Constraints**

- `UNIQUE (city_id, observed_at, units)`: the natural key. Ingestion is an `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`, which refreshes the values and `fetched_at` instead of inserting a duplicate. Retries and repeated calls are safe.
- Check constraints on value ranges (`humidity`/`cloudiness` 0–100, `wind_deg` 0–360, latitude/longitude ranges) and on `units` (`standard` | `metric` | `imperial`).

**Indexes** (driven by the API queries in feature 3)

- `(city_search_name, observed_at)`: "readings for a city, newest first" and "latest for a city".
- `(observed_at)`: time-range queries across all cities.
- The unique constraint's index also serves lookups by `city_id`.

**City matching.** Users type `Florianopolis` or `florianópolis,BR`; OpenWeather returns `Florianópolis`. We store `city_search_name` (computed in Python with Unicode normalization) and normalize the query the same way, optionally also filtering by country code.

## Alternatives considered

- **Normalized schema (`cities` + `readings`, maybe `conditions`)**: avoids repeating the city name and coordinates on each row, but adds joins and a second upsert for little gain at this scale. It is a straightforward later migration if needed.
- **Unique key on `(city_id, observed_at)` only**: then fetching the same observation in imperial would overwrite the metric values, and the row's `units` would silently change. Including `units` keeps each row self-consistent.
- **Always store metric and convert on read**: a cleaner single source of truth, but the assessment explicitly asks for dynamic request parameters, and storing what was requested keeps the data traceable to the raw payload.
- **Only `JSONB`, no typed columns**: flexible, but every query would need JSON operators and there would be no type or range checks.
- **`unaccent()` / `citext` in PostgreSQL for city matching**: needs extensions, and `unaccent` is not immutable, so it cannot be used in a plain index. A normalized column is portable and indexable.
- **`DOUBLE PRECISION` for measurements**: smaller, but binary floating point would show values like `24.309999`. OpenWeather reports at most two decimals.

## Consequences

- Repeating city data per row is accepted denormalization.
- `lang` is not part of the key: fetching the same observation in another language updates `weather_description` and `lang` on the existing row.
- The raw payload lets us backfill new columns from history without calling OpenWeather again.
